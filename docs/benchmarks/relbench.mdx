[RelBench](https://relbench.stanford.edu) (Stanford STAR) benchmarks supervised prediction
over temporal relational databases: **11 databases, 66 tasks** across entity
classification (AUROC), entity regression (MAE/NMAE, R²), recommendation (MAP@K), and the
new v2 autocomplete family. A model receives a multi-table database plus seed rows
(entity id, seed time) and predicts future outcomes, missing attributes, or ranked future
links — with every feature and neighborhood censored at each row's seed time.

All Kapso scores come from the official RelBench evaluator on the official task sets; the
comparison numbers are the methods' own entries on the
[official RelBench leaderboard](https://star-project.stanford.edu/relbench/leaderboard/), read on
2026-10-11. The leaderboard is self-reported and sets no hardware or time budget, so no claim is
made about either. KumoRFM-v2 is on the board as KumoRelational, the open release from the
KumoRFM-2 paper. Neither it nor RT-J has a recommendation entry, so there the bar is ID-GNN, a
RelBench baseline, at 9.3 mean MAP over the same ten tasks. Kapso's entries were submitted by
Leeroo on 2026-08-26 (the board's entry carries the date and its submission issue, 393); the
per-task values are on the board. The campaign records this repository keeps cover one task,
`rel-trial/study-outcome`, run between 2026-07-31 and 2026-08-14 in thirteen lanes with several
test scorings; for the other tasks the board's entry is the record.

## How Kapso runs it

The runner launches `build()` with the bundled `predictive-modelling` harness: the Brief
carries the task's facts (the schema, the label-generating code, the regime, the
prediction contract, the rules), the harness carries the discipline (the sanitized copy,
the temporal protocol, the leakage scan and auditor, the measured practices), and the
provided grader scores every experiment:

1. The candidate's `main.py` runs against a **sanitized, read-only copy** of the database
   built by the harness's sanitizer: the database is physically truncated at the test
   cutoff (or, for autocomplete, post-cutoff target values are blanked and the derived
   columns removed), and the test task table carries only entity ids and timestamps —
   test labels are physically absent from the candidate's process.
2. The candidate writes `val_predictions.npy` and `test_predictions.npy` to
   `$KAPSO_RUN_DATA_DIR` (contract validated: shapes, dtypes, ranges).
3. The grader computes the **official validation metrics** — the search score, oriented
   so that higher is better — and archives every full run; test metrics are never
   computed during the search.
4. After the campaign the runner selects among the archive's registered finals, scores
   the winner **once** on test, runs the harness's leakage scan over its code, and writes
   `final_report.json`.

This is exactly the RelBench protocol: select on validation, report test once.

A starter kit of contract helpers — task loading from the copy, prediction saving and
validation, method choice entirely the agent's — is seeded into every workspace under
`kapso_datasets/`.

## Usage

```bash
# List all native tasks
PYTHONPATH=. python -m benchmarks.relbench.runner --list

# Smoke test on the smallest database
PYTHONPATH=. python -m benchmarks.relbench.runner -s rel-f1 -t driver-position -i 3

# Full run
PYTHONPATH=. python -m benchmarks.relbench.runner -s rel-hm -t user-item-purchase -i 25

# Campaign standard, on Claude Code
PYTHONPATH=. python -m benchmarks.relbench.runner \
    -s rel-trial -t site-sponsor-run -i 30 -d claude_code
```

## CLI options

| Option | Description | Default |
|--------|-------------|---------|
| `-s, --dataset` / `-t, --task` | RelBench dataset/task | Required |
| `-i, --iterations` | `Budget.experiments` | the config's `budget.experiments` |
| `--time-budget-hours` | `Budget.minutes`, in hours | the config's `budget.minutes` |
| `-d, --coding-agent` | The host every role without a `cli` of its own runs on | `codex`, the override file's `host` |
| `--harness` | A harness reference | the bundled `predictive-modelling` |
| `--experience` | Comma-separated experience sources to serve | none |
| `--workspace` / `--resume` | The campaign directory / continue the campaign in it | a fresh directory |
| `--rebuild-cache` | Build the sanitized copy again | reused under its marker |

## Setup

```bash
pip install relbench duckdb pooch pyarrow scikit-learn   # evaluation layer
pip install "relbench[full]" sentence-transformers \
    lightgbm xgboost catboost tqdm                   # modeling stack (GPU machine)
```

Datasets download automatically to `~/.cache/relbench` on first use. See
`benchmarks/relbench/README.md` for the campaign plan, protocol guarantees, and
per-family strategy notes.
