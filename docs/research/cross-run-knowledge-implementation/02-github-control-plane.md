# M2 — GitHub control plane and verified materialization

Parent plan: [`00-orchestrator-plan.md`](00-orchestrator-plan.md)

Depends on: M1.

## Objective

Implement the sole trusted boundary for Git/GitHub reads and writes. It provides
candidate pull-request publication, ordered immutable-release publication,
content-pinned resolution, and transactional local materialization without giving
GitHub credentials or raw Git commands to coding-agent subprocesses.

## Owned responsibilities

- Git and `gh` command execution behind a fakeable typed runner.
- Repository/ref/release/asset discovery and strict response validation.
- `GitHubPublicationRecord` creation and verification.
- Candidate branch and pull-request submission with narrow path/parent limits.
- Draft-upload-verify-publish-CAS release protocol.
- Content-addressed, read-only local artifact cache.
- GitHub authentication diagnostics without reading or persisting secrets.
- Repository bootstrap/ruleset verification used by production validation.

## Command/provider boundary

- [ ] Define a typed command request/result interface accepting argv arrays,
      explicit cwd, timeout from config, and expected output schema.
- [ ] Invoke without a shell; never build command strings from model output.
- [ ] Allow only the exact Git/`gh` operations needed by resolver and publisher.
- [ ] Keep all imports at module top; isolate optional GitHub-specific dependencies
      inside this feature package.
- [ ] Let command failures propagate with complete non-secret diagnostics; do not
      select a fallback transport or retry policy outside configured behavior.
- [ ] Never read authentication environment variables in Kapso code. `git`, `gh`,
      a credential helper, or the GitHub Actions identity owns credential
      discovery.
- [ ] Explicitly construct coding-agent subprocess environments that exclude
      GitHub and OpenAI provider credentials.

Tests use a deterministic fake runner. Unit tests never require network access or
the developer's GitHub authentication.

## Candidate publication

`GitHubCandidatePublisher` accepts only a locally validated candidate envelope:

```text
candidate artifact ID
target repository
expected protected-base commit
allowed path roots
candidate branch prefix
candidate manifest
local working tree
PR title/body generated by trusted code
```

Tasks:

- [ ] Verify target repository/node identity against config.
- [ ] Verify the local diff, changed paths, total bytes, symlinks, submodules, and
      parent tree before any push.
- [ ] Reject changes to workflow, ruleset, secret, release-control, and unexpected
      paths unless the trusted caller's candidate class explicitly owns them.
- [ ] Mint the branch name from the content ID; do not accept a model-supplied ref.
- [ ] Commit the exact candidate manifest/tree with deterministic provenance.
- [ ] Push only the candidate ref and open/update exactly one pull request.
- [ ] Treat replay of the same content as idempotent; reject the same candidate ID
      with different bytes.
- [ ] Record repository, branch, PR, commit, parent, and actor in publication
      telemetry; never record credentials.

The agent may request `submit_candidate` through MCP, but that operation passes a
candidate ID—not arbitrary Git arguments. The gate process invokes this publisher.

## Stable release transaction

`GitHubReleasePublisher` exposes one artifact-neutral protocol used later by M5
and M8:

1. confirm the approved source/manifest commit is the expected protected base;
2. create a draft release/tag at that exact commit;
3. upload every precomputed asset and checksum file;
4. query the release and verify asset names, IDs, sizes, and SHA-256 digests;
5. publish the release so immutable-release controls lock the tag/assets;
6. verify the resulting release attestation/provenance;
7. create `GitHubPublicationRecord`;
8. update `CURRENT.json` in a separate protected commit based on the expected
   prior pointer commit, without force.

- [ ] Never update `CURRENT.json` before the immutable release verifies.
- [ ] A failure before step 8 leaves an inactive orphan release for audit.
- [ ] A CAS conflict returns a typed conflict to the domain publisher, which must
      reload/rebuild; this module does not guess how to merge scientific data or
      expert code.
- [ ] Never mutate/delete a published release or move its tag.
- [ ] Validate GitHub's returned digest against the locally computed digest.
- [ ] Pin immutable release ID and asset IDs as well as human-readable tag/name.

## Resolution and materialization

`GitHubArtifactResolver`:

- [ ] Resolves the protected default-branch head once and reads `CURRENT.json` at
      that commit.
- [ ] Validates repository identity, publication record, tag, source commit,
      immutable-release state, asset set, digests, and trusted publisher.
- [ ] Returns immutable locators only; callers cannot request `latest` after
      resolution.
- [ ] Downloads assets to a same-filesystem staging directory.
- [ ] Verifies archive path safety, manifest schema, all content hashes, and the
      expected artifact ID before extraction becomes visible.
- [ ] Flushes and atomically renames to a cache path keyed by content identity.
- [ ] Marks the completed cache read-only and writes a verification receipt.
- [ ] Reuses a cache entry only when its receipt and complete tree/package digest
      verify.
- [ ] Exposes explicit cache inspection/pruning; never removes a pinned entry.

Partial downloads/extractions have no committed cache marker and are never
returned. Missing or corrupt cache content raises rather than triggering an
unrecorded alternate source.

## Repository policy contract

Production repositories must enforce:

- private visibility unless an explicit scope policy permits public artifacts;
- protected default branches and release-tag patterns;
- pull requests, required status checks, designated reviews, stale-review
  dismissal, force-push/deletion blocking, and linear/auditable history;
- immutable releases;
- separate read, candidate, and stable-publisher identities; and
- no candidate-publisher bypass of stable branch/tag rules.

M2 supplies a read-only diagnostic that reports the observed policy. It does not
silently modify organization/repository administration settings.

## Tests

- Assert exact safe argv for every Git/`gh` call.
- Reject shell metacharacters, invalid repository/ref names, unexpected paths,
  symlinks, submodules, oversized candidates, and stale parents.
- Prove same-candidate replay is idempotent and conflicting replay fails.
- Inject failure after draft creation, each asset upload, release publication, and
  before/after pointer commit.
- Prove `CURRENT.json` cannot reference a draft or incomplete release.
- Simulate two publishers from one base and require one typed CAS conflict.
- Reject replaced tags, missing assets, digest mismatch, forged publisher, and
  inconsistent repository identity.
- Inject partial download/extraction and prove no cache entry becomes visible.
- Verify cache reuse, corruption detection, read-only permissions, and pinned-entry
  retention.
- Prove coding-agent environments contain no GitHub/OpenAI credentials.

## Definition of done

- M3/M5/M8/M9 can use typed GitHub operations without invoking GitHub directly.
- Candidate publication cannot advance a stable ref or modify forbidden paths.
- Stable publication has the documented crash and CAS semantics.
- A release can be resolved and materialized from only its publication record and
  configured trust roots.
- Offline unit tests cover all failure boundaries; real GitHub tests are deferred
  to M10.

## Non-goals

- Scientific merge/admission decisions.
- Building snapshot or expert release contents.
- Creating or storing GitHub secrets.
- Automatically administering organization rulesets.
