The Kapso plugin is one directory, [`plugin/`](https://github.com/Leeroo-AI/kapso/tree/main/plugin) in the repository, that Claude Code, Codex and Cursor each read through their own manifest. It carries the commands you type, the skills the agent follows, and the MCP server that serves your session what Kapso knows. With it, a coding agent sets Kapso up to a green `doctor`, turns a wish into a brief with an evaluation Kapso can protect, launches the campaign detached and hands you the watch line, answers a campaign that is waiting on you, tells a slow run from a dead one, reviews a finished run from its record, and writes a harness from your repository. Without it, the same agent reads the package source until its turn budget runs out.

## Install

```bash
# Claude Code
claude plugin marketplace add Leeroo-AI/kapso
claude plugin install kapso@kapso

# Codex
codex plugin marketplace add Leeroo-AI/kapso
codex plugin add kapso@kapso
codex mcp add kapso -- kapso-mcp          # the server, once: Codex does not expose a plugin's MCP tools to a session
```

Codex drops a server that has not answered within ten seconds, and `kapso-mcp` imports the package before it answers, which a busy machine can stretch past that; `/kapso:setup` gives the server a minute (`startup_timeout_sec = 60` under `[mcp_servers.kapso]` in `~/.codex/config.toml`), and a registration by hand should too.

The repository is the marketplace: `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json` at its root name the one plugin at `./plugin`. The plugin's version is the package's, so install the package at the same version (`/kapso:setup` does, pinned). Cursor reads the same directory through `.cursor-plugin/plugin.json`; point Cursor's plugin installer at the repository. Cursor was not part of this release's proof: the skills and the MCP entry are the files the other two hosts ran.

To try the plugin from a clone without installing it, Claude Code takes `claude --plugin-dir ./plugin` for one session.

## What the plugin ships

Ten commands, each a short prompt that hands over to a skill with your request:

| Command | What it does |
|---|---|
| `/kapso:setup` | Install Kapso, run the logins, write the keys to `.env`, verify with `kapso doctor build --json` |
| `/kapso:build <wish>` | Discover the repository, write `kapso-brief.md`, get the evaluation approved, launch detached |
| `/kapso:watch [campaign]` | How a campaign is doing, in three lines; with no path, every campaign alive or waiting |
| `/kapso:inbox [campaign] [note]` | What a paused campaign is waiting on you for, and the reply that resumes it |
| `/kapso:resume <campaign>` | The diagnosis first, then the resume from the checkpoint |
| `/kapso:review [campaign]` | What a finished run did: what won, the evidence, what was voided, the next action |
| `/kapso:learn [campaign]` | Bank what the campaign taught, detached; then the offer to serve the bank to every session |
| `/kapso:deploy [campaign] [--target]` | Deploy the delivered solution, prove one call, hand back the handle |
| `/kapso:harness new\|improve\|check\|…` | Write a harness from the repository, improve one from a run, or the verbs |
| `/kapso:experience add\|list\|share\|…` | Your bank, the team's, an ingested corpus: what a build or this session is served |

Six skills, the procedures the commands follow and the agent reaches on its own when a request matches their descriptions:

| Skill | When it fires | What it holds |
|---|---|---|
| `kapso-setup` | "set up kapso", a red `doctor` | Detect before asking; install with the method the machine has; the logins; the keys, never printed; `doctor` to green; three closing lines |
| `kapso-build` | "build X and verify it", "get the AUC above the 0.85 target", `/kapso:build` | Listen for the two things; discover in silence; the brief in one message; at most one more round; the detached launch and the handoff |
| `kapso-evaluation` | called by `kapso-build` | The evaluator contract; an evaluator found is audited, a criterion without one gets an evaluator built, neither gets candidates proposed; one approval |
| `kapso-harness` | "write a harness for X", "the attempts keep doing Y" | A first harness proposed from the repository within two minutes; one question per silent module; `check` to green; the improve loop from a trace |
| `kapso-review` | "what did it do", "is it safe to merge" | The trace and the record read; one message: the diff in outline, the evidence with its version, the voided attempts, the spend, the next action |
| `kapso` | "how is the campaign", "it died", "stop it", "deploy it" | The operating facts: the handoff, the inbox, slow against stalled against dead, the stop and the resume, learn, experience, deploy, the config |

The skills are one file each under [`plugin/skills/`](https://github.com/Leeroo-AI/kapso/tree/main/plugin/skills), the same text for every host, with a Codex sidecar beside each. `kapso-evaluation` is hidden from Claude Code's menu and still the agent's to call. A trigger suite under `plugin/evals/` checks that each skill fires on its own phrasings and stays quiet on its near misses, on both hosts.

## The first session

```text
/kapso:setup
/kapso:build get the churn model's ROC AUC above 0.85 without changing the prediction contract
```

On Codex the same two steps are `$kapso-setup` and `$kapso-build …`. A session started before the setup sees the tools it installed after `/mcp` reconnects (Claude Code) or in a new session (Codex).

Setup detects what the machine has, installs what is missing, starts the logins and shows you the links, asks only for the keys your next step needs, and ends when `kapso doctor build --json` is green: under five minutes, at most three questions. Build reads the repository in silence, hands the evaluation to `kapso-evaluation`, and sends one message: what it found with the evidence, the brief as `kapso-brief.md`, the evaluation's protocol when one was built or changed, and the one thing to confirm. On "go" it launches with `--detach` and hands you `kapso watch <campaign> --follow`. The campaign outlives the session; `WAITING ON YOU` is a pause answered through `/kapso:inbox`. See [Your first build](/docs/first-build) for what the campaign does from there.

## What a session is served

The plugin's MCP server, `kapso-mcp`, starts with the session and serves it the campaign verbs as tools (`kapso_build_start`, `kapso_status`, `kapso_stop`), web research, the repository's memory when a campaign built one, the experiment history inside a campaign directory, and the bank tools over what the project's config lists:

```yaml
# kapso-config.yaml, at the project root
experience:
  session_sources: [mine:all]
```

That line serves every later session of the project your bank; `/kapso:learn` offers it once a campaign has been banked. It serves sessions, not builds: a build loads what its brief or `--experience` names. A listed source that does not exist leaves its tools off, named in the server's instructions with the line that makes it, and the server connects whatever is off. `kapso-mcp` reads `kapso-config.yaml` at the repository root when no `--config` is passed, and prints its version and config line on start. On Claude Code the server's state is under `/mcp` and its lines in the session's debug log; on Codex, `codex mcp list` and `~/.codex/log/`.

A campaign's own sessions never launch a campaign. On Claude Code they run with the plugin switched off (no skill, no command, no campaign tool). Codex has no per-session switch, so there Kapso writes an execpolicy rule into each session's workspace that rejects `kapso build`, `kapso learn` and `kapso deploy`, and disables the plugin's server for the session: the skills' text may be read, the verbs are refused (verified live, the rule in a gitignored subdirectory of the clone included).

## The second engineer

A teammate with the plugin installed reads the bank you shared by its reference; a bank needs no `add` (loading fetches it into their store the first time):

```bash
kapso experience share https://github.com/acme/kapso-bank.git     # you, once; create the repository first
kapso build --experience acme/kapso-bank@main --config kapso-config.yaml …   # them: a build served your bank
kapso experience update --config kapso-config.yaml                           # them, whenever they want your newest lessons
```

Their `session_sources` lists `acme/kapso-bank@main` beside `mine:all`, so their sessions are served it too (a session fetches a listed bank the first time its remote answers), and `kapso experience list` shows it under the banks they read. To hand the plugin itself to everyone who opens the repository, Claude Code reads a marketplace from the project's settings:

```json
// .claude/settings.json
{"extraKnownMarketplaces": {"kapso": {"source": {"source": "github", "repo": "Leeroo-AI/kapso"}}}}
```

## Without the plugin

OpenCode reads the skills as a folder: `ln -s <clone>/plugin/skills .opencode/skills` loads the six at once (skills only: the commands are Claude Code's, and OpenCode's own `mcp` configuration takes `kapso-mcp` as a stdio server). Any host takes the server alone:

```bash
claude mcp add kapso -- kapso-mcp --experience mine:all
codex mcp add kapso -- kapso-mcp --experience mine:all
```

`--experience` replaces the config's list for that session; an empty string loads nothing. The one operating skill, [`plugin/skills/kapso/SKILL.md`](https://github.com/Leeroo-AI/kapso/blob/main/plugin/skills/kapso/SKILL.md), is also what an agent reading the repository is told to start from.

## The docs in the same agent

The plugin gives the agent the procedures; the documentation gives it the facts. The site runs a Model Context Protocol server at `https://docs.leeroo.com/mcp` that exposes search and retrieval over every published page, so an agent can look up a configuration key or a flag and quote the [CLI reference](/docs/reference/cli) or the [Python API](/docs/reference/kapso-api) as published from `main`; the server has one endpoint and no version selection, so what it serves is the latest published documentation, which can run ahead of the release you installed. The server is read-only and needs no key.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http kapso-docs https://docs.leeroo.com/mcp
    ```
    Then, in a session, ask about Kapso as you normally would. Claude Code calls the server when a question needs the docs.
  </Tab>
  <Tab title="Codex CLI">
    ```bash
    codex mcp add kapso-docs --url https://docs.leeroo.com/mcp
    ```
    The entry lands in `~/.codex/config.toml` and is shared by the Codex CLI and IDE extension.
  </Tab>
  <Tab title="Cursor">
    Add the server to `~/.cursor/mcp.json` (or the project's `.cursor/mcp.json`):
    ```json
    {
      "mcpServers": {
        "kapso-docs": { "url": "https://docs.leeroo.com/mcp" }
      }
    }
    ```
  </Tab>
</Tabs>

Every page is also served as plain Markdown, the form agents fetch on their own: `https://docs.leeroo.com/llms.txt` lists every page with its title and description, `https://docs.leeroo.com/llms-full.txt` holds the whole site in one file, and `.md` appended to any page address (or `Accept: text/markdown`) returns that page alone. Paste a page address into a session and the agent reads the Markdown, not the rendered HTML.

Kapso itself drives Claude Code and Codex as the engine that implements each experiment inside a campaign. That is the other direction, described under [coding agents in Kapso](/docs/evolve/coding-agents).

## Measured

The operating skill was first measured on Kapso 0.4.x, the same prompts with and without it on three hosts; the [findings log](https://github.com/Leeroo-AI/kapso/blob/main/docs/plans/coding-agent-skill-findings.md) has the tables and every product defect the runs turned up. This release's plugin is measured by its trigger suite (`claude plugin eval plugin` on Claude Code, `scripts/redesign/plugin_round.sh codex-triggers` on Codex) and by the proof round recorded in `docs/plans/redesign/wp7-plugin.md`.
