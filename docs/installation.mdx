Kapso sends every model call through a coding-agent CLI. Install those CLIs and log in **before** installing the Python package — on its own the package cannot reach a model, and `kapso evolve` will stop in seconds rather than fail deep inside a run.

## Prerequisites

| You need | Why | Checked by |
|----------|-----|------------|
| Node.js 18 or newer | Both coding-agent CLIs are npm packages | `node` |
| Codex CLI, logged in | Research, judging and utility calls | `codex authenticated` |
| Claude Code CLI, logged in | Ideation and implementation in the default `GENERIC` mode | `claude authenticated` |
| Python 3.10 or newer | The `leeroo-kapso` package | — |
| An OpenAI API key | Embeddings for knowledge search and memory. Not used for generation | `OPENAI_API_KEY (embeddings)` |
| Git | Kapso commits every experiment to a branch | `git` |

## Install Kapso

<Steps>
  <Step title="Install and log in to the coding-agent CLIs">
    ```bash
    npm install -g @openai/codex
    codex login

    npm install -g @anthropic-ai/claude-code
    claude auth login
    ```

    Both logins are interactive and open a browser. To authenticate without a
    browser, see [Using API keys instead of a CLI login](#using-api-keys-instead-of-a-cli-login).
  </Step>

  <Step title="Add an OpenAI key for embeddings">
    Create a `.env` file in the directory you will run Kapso from:

    ```bash
    echo 'OPENAI_API_KEY=sk-...' >> .env
    ```

    This key is used only to embed text for knowledge search and memory. Generation runs through the CLIs above.
  </Step>

  <Step title="Install the package">
    ```bash
    pip install leeroo-kapso
    ```

    To work from a source checkout instead:

    ```bash
    git clone https://github.com/leeroo-ai/kapso.git
    cd kapso
    conda create -n kapso_conda python=3.12
    conda activate kapso_conda
    pip install -e .
    ```
  </Step>

  <Step title="Verify the machine is ready">
    ```bash
    kapso doctor
    ```

    Every required check must read `[OK ]` before you run anything else.
  </Step>
</Steps>

## How do I check my setup?

`kapso doctor` reports what **your config** requires, and names one fix for anything missing:

```bash
kapso doctor
```

```text
kapso doctor
====================================================================
  [OK ] node
  [OK ] codex CLI
  [OK ] codex authenticated
  [OK ] claude CLI
  [OK ] claude authenticated
  [OK ] git
  [OK ] OPENAI_API_KEY (embeddings)
  [OK ] deploy target docker
  [-- ] deploy target modal
         needed by  only needed for deploy(strategy=DeployStrategy.MODAL)
         fix        pip install modal && modal token new
====================================================================
Required checks passed (9 checked). 1 optional item(s) marked [-- ] only limit features you may not need.
```

Your own list will be longer or shorter than this one. It is derived from your config, so enabling knowledge search adds Weaviate and Neo4j rows, and configuring a lesson bank adds a remote-reachability row.

These are the same checks each verb runs before it does any work, so `doctor` cannot disagree with what a run will do. The command exits non-zero when a required item is missing, which makes it usable in CI.

### What the markers mean

| Marker | Meaning |
|--------|---------|
| `[OK ]` | Present and working |
| `[FAIL]` | Required by your config and missing. The run will stop |
| `[-- ]` | Optional. Its absence only removes a feature you may not need |

Each failing item prints three lines: `reason` for what is wrong, `needed by` for the config key that wants it, and `fix` for the command that resolves it.

### How do I check just one command's requirements?

Name a verb to narrow the report to that verb's own requirements. Requirements follow your config, so a verb that never calls Codex is never asked for it:

```bash
kapso doctor research
```

```text
kapso doctor research
====================================================================
  [OK ] node
  [OK ] codex CLI
  [OK ] codex authenticated
====================================================================
Required checks passed (3 checked).
```

```bash
kapso doctor evolve
```

```text
kapso doctor evolve
====================================================================
  [OK ] node
  [OK ] claude CLI
  [OK ] claude authenticated
  [OK ] git
====================================================================
Required checks passed (4 checked).
```

The five verbs are `research`, `learn_knowledge`, `evolve`, `learn` and `deploy`. With no verb, `doctor` reports the union of all five.

### How do I confirm my models are actually reachable?

Add `--models` to fire a one-token live call per configured CLI and model pair. A subscription cap or a revoked login surfaces here in seconds instead of hours into a campaign:

```bash
kapso doctor evolve --models
```

<Note>
  `--models` spends a small number of real tokens. The plain `doctor` makes no model calls.
</Note>

## Using API keys instead of a CLI login

Each agent block in the config carries an `auth_mode`. The shipped default is `oauth`, which uses the CLI's own stored login:

| `auth_mode` | Credential used |
|-------------|-----------------|
| `oauth` | The CLI's stored login from `claude auth login` |
| `api_key` | `ANTHROPIC_API_KEY` from your environment |
| `auto` | Either, whichever is present |

For non-interactive environments such as CI, put a token in `.env` instead of logging in:

```bash
CLAUDE_CODE_OAUTH_TOKEN=...
CODEX_API_KEY=...
```

## Optional: knowledge-graph backends

`learn_knowledge()` and `kapso index_kg` store into a local Weaviate and Neo4j. Both run in Docker. From a source checkout:

```bash
bash scripts/start_infra.sh
```

| Service | Purpose | URL | Credentials |
|---------|---------|-----|-------------|
| Weaviate | Vector store for embeddings | `http://localhost:8080` | Anonymous |
| Neo4j | Graph store for relationships | `http://localhost:7474` | `neo4j` / `password` |

```bash
bash scripts/stop_infra.sh              # stop, keep the data
bash scripts/stop_infra.sh --volumes    # stop and wipe the data
```

`kapso doctor` reports both as `Weaviate (localhost:8080)` and `Neo4j (localhost:7687)` when your config enables knowledge search.

## Optional: benchmarks

The benchmark harnesses live in the source checkout under `benchmarks/` and each needs its upstream repository installed first.

<Tabs>
  <Tab title="MLE-Bench">
    Kaggle competition problems. Needs Git LFS.

    ```bash
    git clone https://github.com/openai/mle-bench.git
    cd mle-bench
    git lfs install
    git lfs fetch --all
    git lfs pull
    pip install -e .
    cd ..

    pip install -r benchmarks/mle/requirements.txt
    ```

    See [MLE-Bench](/docs/benchmarks/mle-bench) for how to run it.
  </Tab>
  <Tab title="ALE-Bench">
    AtCoder algorithmic optimization problems. Needs Docker and `libcairo2-dev`.

    ```bash
    git clone https://github.com/SakanaAI/ALE-Bench.git
    cd ALE-Bench
    pip install .
    pip install ".[eval]"
    bash ./scripts/docker_build_202301.sh $(id -u) $(id -g)
    cd ..
    ```

    See [ALE-Bench](/docs/benchmarks/ale-bench) for how to run it.
  </Tab>
  <Tab title="RelBench">
    Predictive tasks over relational databases. Installed from PyPI.

    ```bash
    pip install relbench
    ```

    See [RelBench](/docs/benchmarks/relbench) for how to run it.
  </Tab>
</Tabs>

## Optional: Leeroopedia MCP

[Leeroopedia](https://leeroopedia.com) is a curated knowledge base of ML and AI frameworks. Kapso agents query it during ideation and implementation to look up APIs, build plans and diagnose failures.

```bash
pip install leeroopedia-mcp
```

Get a key at [app.leeroopedia.com](https://app.leeroopedia.com), then add it to `.env`:

```bash
LEEROOPEDIA_API_KEY=kpsk_...
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="doctor says a CLI is missing but I just installed it">
    Global npm binaries have to be on your `PATH`. Confirm the shell can see them:

    ```bash
    which codex claude node
    ```

    If `npm install -g` wrote somewhere outside your `PATH`, `npm prefix -g` shows where.
  </Accordion>

  <Accordion title="doctor says a CLI is not authenticated">
    The login is stored per machine and expires. Re-run it:

    ```bash
    codex login
    claude auth login
    ```

    Codex stores its login at `~/.codex/auth.json`. Claude Code answers `claude auth status`.
  </Accordion>

  <Accordion title="Weaviate or Neo4j will not start">
    Check the container logs:

    ```bash
    docker compose -f services/infrastructure/docker-compose.yml logs
    ```

    Ports 8080, 50051, 7474 and 7687 must be free. If one is taken, change the mapping in `services/infrastructure/docker-compose.yml`.
  </Accordion>

  <Accordion title="A run fails partway through on a model error">
    Probe the models directly rather than guessing:

    ```bash
    kapso doctor evolve --models
    ```

    A capped subscription or an expired login shows up here immediately.
  </Accordion>
</AccordionGroup>
