Kapso sends every model call through a coding-agent CLI. Install those CLIs and log in **before** installing the Python package — on its own the package cannot reach a model, and `kapso evolve` will stop in seconds rather than fail deep inside a run.

## Prerequisites

| You need | Why | Checked by |
|----------|-----|------------|
| Node.js 18 or newer | Both coding-agent CLIs are npm packages | `node` |
| Codex CLI, logged in | Research, judging and utility calls | `codex authenticated` |
| Claude Code CLI, logged in | Ideation and implementation in the default `GENERIC` mode | `claude authenticated` |
| Python 3.10 or newer | The `leeroo-kapso` package | — |
| An OpenAI API key (optional) | Embeddings, never generation: the knowledge graph, and semantic search over past experiments when `models.embedding` is set. A stock install needs neither | `OPENAI_API_KEY (embeddings: https://api.openai.com/v1)`, only when something will embed |
| Git | Kapso commits every experiment to a branch | `git` |

## Install Kapso

<Steps>
  <Step title="Install and log in to the coding-agent CLIs">
    ```bash
    npm install -g @openai/codex
    codex login

    npm install -g @anthropic-ai/claude-code
    claude auth login
    ```

    Both logins are interactive and open a browser. To authenticate without a
    browser, see [Using API keys instead of a CLI login](#using-api-keys-instead-of-a-cli-login).
  </Step>

  <Step title="Optional: an OpenAI key for embeddings">
    Only the knowledge graph and semantic search over past experiments embed text, and generation never touches the OpenAI API. Nothing in a stock install needs the key. When you turn either on (a `kg_index`, `learn_knowledge`, or `models.embedding` in your config), put the key in a `.env` file in the directory you run Kapso from:

    ```bash
    echo 'OPENAI_API_KEY=sk-...' >> .env
    ```
  </Step>

  <Step title="Install the package">
    ```bash
    pip install leeroo-kapso
    ```

    The package is `leeroo-kapso`. The PyPI package named `kapso` is an unrelated WhatsApp tool that installs a `kapso` command of its own and shadows this one; if it is present, `pip uninstall kapso` first.

    To work from a source checkout instead:

    ```bash
    git clone https://github.com/leeroo-ai/kapso.git
    cd kapso
    conda create -n kapso_conda python=3.12
    conda activate kapso_conda
    pip install -e .
    ```
  </Step>

  <Step title="Verify the machine is ready">
    ```bash
    kapso doctor
    ```

    Every required check must read `[OK ]` before you run anything else.
  </Step>
</Steps>

## Connect Leeroopedia (recommended)

[Leeroopedia](https://leeroopedia.com) is a hosted knowledge base of ML and AI frameworks. With a key in `.env`, every campaign session can ask it how a framework actually behaves, have its plan reviewed, pull documented hyperparameter ranges and diagnose a failed run. There is nothing to install: sessions connect to Leeroopedia's hosted MCP server. Sign up at [app.leeroopedia.com](https://app.leeroopedia.com/dashboard) (new accounts get $20 of free credit), copy your key, and add it:

```bash
LEEROOPEDIA_API_KEY=kpsk_...
```

`kapso doctor` confirms the gate is live. Without a key the campaign still runs; the launch banner says the gate is off and how to turn it on. What each node consulted, and the credits used, appear in `kapso watch --tree` and the campaign's final summary. See [MCP gates](/docs/evolve/mcp-gates) for what the agent is told about it.

## How do I check my setup?

`kapso doctor` reports what **your config** requires, and names one fix for anything missing:

```bash
kapso doctor
```

```text
kapso doctor
====================================================================
  [OK ] node
  [OK ] codex CLI
  [OK ] codex authenticated
  [OK ] claude CLI
  [OK ] claude authenticated
  [OK ] git
  [OK ] OPENAI_API_KEY (embeddings: https://api.openai.com/v1)
  [OK ] deploy target docker
  [-- ] deploy target modal
         needed by  only needed for deploy(strategy=DeployStrategy.MODAL)
         fix        pip install modal && modal token new
====================================================================
Required checks passed (9 checked). 1 optional item(s) marked [-- ] only limit features you may not need.
```

Your own list will be longer or shorter than this one. It is derived from your config, so enabling knowledge search adds Weaviate and Neo4j rows, and configuring a lesson bank adds a remote-reachability row.

These are the same checks each verb runs before it does any work, so `doctor` cannot disagree with what a run will do. The command exits non-zero when a required item is missing, which makes it usable in CI.

### What the markers mean

| Marker | Meaning |
|--------|---------|
| `[OK ]` | Present and working |
| `[FAIL]` | Required by your config and missing. The run will stop |
| `[-- ]` | Optional. Its absence only removes a feature you may not need |

Each failing item prints up to three lines: `reason` for what is wrong, `needed by` for the config key that wants it, and `fix` for the command that resolves it.

### How do I check just one command's requirements?

Name a verb to narrow the report to that verb's own requirements. Requirements follow your config, so a verb that never calls Codex is never asked for it:

```bash
kapso doctor research
```

```text
kapso doctor research
====================================================================
  [OK ] node
  [OK ] codex CLI
  [OK ] codex authenticated
====================================================================
Required checks passed (3 checked).
```

```bash
kapso doctor evolve
```

```text
kapso doctor evolve
====================================================================
  [OK ] node
  [OK ] claude CLI
  [OK ] claude authenticated
  [OK ] codex CLI
  [OK ] codex authenticated
  [OK ] git
====================================================================
Required checks passed (6 checked).
```

The five verbs are `research`, `learn_knowledge`, `evolve`, `learn` and `deploy`. With no verb, `doctor` reports the union of all five.

### How do I confirm my models are actually reachable?

Add `--models` to fire a one-token live call per configured CLI and model pair. A revoked login, or a model your plan does not include, surfaces here in seconds instead of hours into a campaign. A usage cap on a model you can serve does not: a one-token probe passes until the cap is hit.

```bash
kapso doctor evolve --models
```

<Note>
  `--models` spends a small number of real tokens. The plain `doctor` makes no model calls.
</Note>

## Using API keys instead of a CLI login

Each agent block in the config carries an `auth_mode`. The shipped default is `oauth`, which uses the CLI's own stored login:

| `auth_mode` | Credential used |
|-------------|-----------------|
| `oauth` | The CLI's stored login from `claude auth login` |
| `api_key` | `ANTHROPIC_API_KEY` from your environment |
| `auto` | Either, whichever is present; never Bedrock |
| `bedrock` | AWS credentials (`AWS_BEARER_TOKEN_BEDROCK`, an access key pair, or `AWS_PROFILE`) with `aws_region` set in the config; models are named by Bedrock inference profile id. See [coding agents](/docs/evolve/coding-agents#how-do-i-authenticate-claude-code) |

For non-interactive environments such as CI, put a token in `.env` instead of logging in:

```bash
CLAUDE_CODE_OAUTH_TOKEN=...
CODEX_API_KEY=...
```

## Optional: Knowledge-graph backends

`learn_knowledge()` and `kapso index_kg` store into a local Weaviate and Neo4j. Both run in Docker. From a source checkout:

```bash
bash scripts/start_infra.sh
```

| Service | Purpose | URL | Credentials |
|---------|---------|-----|-------------|
| Weaviate | Vector store for embeddings | `http://localhost:8080` | Anonymous |
| Neo4j | Graph store for relationships | `http://localhost:7474` | `neo4j` / `password` |

```bash
bash scripts/stop_infra.sh              # stop, keep the data
bash scripts/stop_infra.sh --volumes    # stop and wipe the data
```

`kapso doctor` reports both as `Weaviate (localhost:8080)` and `Neo4j (localhost:7687)` when your config enables knowledge search.

## Troubleshooting

<AccordionGroup>
  <Accordion title="doctor says a CLI is missing but I just installed it">
    Global npm binaries have to be on your `PATH`. Confirm the shell can see them:

    ```bash
    which codex claude node
    ```

    If `npm install -g` wrote somewhere outside your `PATH`, `npm prefix -g` shows where.
  </Accordion>

  <Accordion title="doctor says a CLI is not authenticated">
    The login is stored per machine and expires. Re-run it:

    ```bash
    codex login
    claude auth login
    ```

    Codex stores its login at `~/.codex/auth.json`. Claude Code answers `claude auth status`.
  </Accordion>

  <Accordion title="Weaviate or Neo4j will not start">
    Check the container logs:

    ```bash
    docker compose -f services/infrastructure/docker-compose.yml logs
    ```

    Ports 8080, 50051, 7474 and 7687 must be free. If one is taken, change the mapping in `services/infrastructure/docker-compose.yml`.
  </Accordion>

  <Accordion title="A run fails partway through on a model error">
    Probe the models directly with `kapso doctor evolve --models` — see [How do I confirm my models are actually reachable?](#how-do-i-confirm-my-models-are-actually-reachable)
  </Accordion>
</AccordionGroup>

## Set up through your coding agent

Paste this into Claude Code, Codex or OpenCode and it walks the steps above with you, hands you the sign-in links, asks for the keys instead of hunting for them, and verifies with `kapso doctor`:

```text
I want to set up Kapso, the open-source software factory by Leeroo (PyPI package leeroo-kapso, docs at https://docs.leeroo.com), on this machine so you can run it from this session. Explain the commands you plan to run, then run them. Do nothing beyond these steps, and never print a key or token.

1. Prerequisites. Check `node --version` (18 or newer), `python3 --version` (3.10 or newer) and `git --version`. Install whatever is missing the way this OS installs software; ask me before using sudo.

2. Coding-agent CLIs. Kapso sends every model call through Claude Code and Codex; there is no API-key fallback for generation. Install both:
   npm install -g @anthropic-ai/claude-code @openai/codex
   If a global npm install needs root, install with --prefix "$HOME/.local" and put "$HOME/.local/bin" on PATH instead.

3. Logins. Run `claude auth status` and `codex login status`. For each one that is not logged in, start the login (`claude auth login`; `codex login`, or `codex login --device-auth` on a machine without a browser), show me the sign-in URL and any one-time code, and wait for me. If a step needs a code pasted back into the terminal, tell me and I will do it in my own terminal. Re-check both statuses before continuing.

4. Keys. Write what I give you to a `.env` file in this directory (Kapso reads `.env` from the directory it runs in):
   LEEROOPEDIA_API_KEY=...   recommended: lets campaigns consult Leeroopedia, a hosted knowledge base of ML and AI frameworks; nothing to install, and a new account at https://app.leeroopedia.com/dashboard comes with $20 of free credit
   OPENAI_API_KEY=...        optional: only for embeddings — the knowledge graph, and semantic search over past experiments once models.embedding is set in the config; generation never uses it
   If I do not have one of them, continue and tell me which doctor row will report it.

5. Package. In the Python environment I use here (if none is active, create `.venv` in this directory, use it from now on, and tell me):
   pip show kapso        # the PyPI package named `kapso` is an unrelated tool that shadows the command; if present: pip uninstall -y kapso
   pip install leeroo-kapso

6. Verify. Run `kapso doctor evolve`: every required row must read `[OK ]`; fix what it names and rerun. Then run `kapso doctor` and tell me what its `[-- ]` rows would enable; the Weaviate and Neo4j rows belong to the knowledge-graph features and need Docker, so leave them unless I ask. Finish with `kapso doctor evolve --models`, which spends a few tokens to confirm each configured model is reachable.

7. The Kapso skill. Install the skill written for you, so you operate Kapso the way its docs say:
   git clone --depth 1 https://github.com/Leeroo-AI/kapso /tmp/kapso-src
   Claude Code:  mkdir -p .claude/skills   && cp -r /tmp/kapso-src/skills/claude-code/kapso .claude/skills/kapso
   Codex:        mkdir -p .agents/skills   && cp -r /tmp/kapso-src/skills/codex/kapso .agents/skills/kapso
   OpenCode:     mkdir -p .opencode/skills && cp -r /tmp/kapso-src/skills/opencode/kapso .opencode/skills/kapso
   Then load it. Ask me whether to also connect the docs: `claude mcp add --transport http kapso-docs https://docs.leeroo.com/mcp` or `codex mcp add kapso-docs --url https://docs.leeroo.com/mcp`.

8. Finish with a short overview of what you can now do, and do not start a campaign until I give you a goal:
   - run a campaign toward a measurable goal, in the background: kapso evolve --goal "<metric and target>" --initial-repo . --eval-dir <judge dir> --output ../<campaign>
   - follow it: kapso watch ../<campaign> --follow; answer a pause (WAITING ON YOU): kapso inbox
   - bank what it taught: Kapso().learn("../<campaign>"); ship the winner: kapso deploy --solution-path ../<campaign> --strategy local
```

The last step installs the [Kapso skill](/docs/coding-agent-skills), which has the agent run `kapso doctor` first, name the right package, and launch campaigns in the background with the handoff you need.
