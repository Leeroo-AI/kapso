# Cross-Run Operations

Kapso has one cross-run operating model: task bindings select a configured scope,
and that scope resolves immutable knowledge, expert, and security releases from
GitHub. Task inputs never contain repository names or mutable branch references.

## State and output

Pass the same config, mode, and owner-private absolute state root to every
operation. Commands emit canonical JSON containing content IDs, GitHub commit and
release identities, validation state, and a next action. They never emit credential
values or raw captured content.

```bash
kapso cross-run production-smoke \
  --config src/kapso/config.yaml \
  --mode GENERIC \
  --state-root /var/lib/kapso-validation \
  --stages preflight bootstrap-authorities github-read embeddings \
           docker-authority knowledge-publication coding-agent-ideation \
           task-adapter-bootstrap expert-proposal \
           expert-validation-enrollment
```

Stages run only in canonical order and append to one durable receipt at
`.kapso/cross_run/production_validation/production-smoke-receipt.json`. Repeating
a completed stage verifies and returns the same receipt without repeating paid or
remote work. A changed config, fixture, stage order, or corrupt receipt fails.

Preflight reports evaluator issuer-to-root coverage and the pinned image identity
without exposing public-key or credential bytes. Missing roots or a missing image
may leave read-only diagnostics usable, but validation and execution fail closed.

`task-adapter-bootstrap` verifies the configured content-pinned image, then
publishes and activates one deterministic public transport adapter for every task
binding in the scope. These adapters exercise the real validation and release
matrix contracts; they are synthetic transport fixtures, not benchmark evidence.

`expert-validation-enrollment` loads the exact E0 candidate from the prior stage,
enters it into the durable validation state machine, and stops at the first signed
evaluator boundary (`contract_schema`). Advancing beyond that point requires the
configured independent evaluator authority; the smoke never manufactures a
passing decision.

## Normal lifecycle

1. `production-smoke` checks providers and bootstraps only the explicitly selected
   synthetic authorities.
2. `capture` exports a reconciled run frontier into a sanitized bundle.
3. `publish-knowledge` projects admitted records and publishes an immutable
   snapshot with a compare-and-swap update to `CURRENT.json`.
4. `propose-expert` runs the configured coding-agent proposer and stores a sealed
   candidate; the proposer cannot approve it.
5. Repeated `validate-expert` operations advance the exact expected validation
   transition. Signed evaluator stages, automated reviews, source replay, release
   matrix, and publication eligibility remain distinct authorities.
6. `publish-expert` accepts only an eligible candidate and publishes a history-free
   source release plus complete evidence archive.
7. `resolve-launch` resolves current immutable releases, task adapter, starting
   artifacts, security state, and compatibility evidence before creating a run.

Read-only diagnosis after bootstrap:

```bash
kapso cross-run inspect --config src/kapso/config.yaml --mode GENERIC \
  --scope-id ml_ai --state-root /var/lib/kapso

kapso cross-run verify --config src/kapso/config.yaml --mode GENERIC \
  --scope-id ml_ai --state-root /var/lib/kapso
```

Mutation requests are canonical JSON files. They must name complete content IDs and
the current expected transition or parent identity; a stale caller retries from a
fresh read rather than forcing an update.

## Evidence interpretation

A successful transport smoke proves authentication, immutability, deterministic
materialization, OpenAI embedding identity, bounded Docker authority, and audited
coding-agent access. It does not prove scientific transfer benefit. Claim that only
from matched task runs with equal budgets and evaluator fingerprints.

On a clean state root, knowledge publication first authenticates the repository's
current snapshot and imports its source facts into the local catalog. If the exact
configured smoke bundle is already present, the stage recovers without an embedding
call or GitHub write. Otherwise it publishes one direct run-bundle and prior-idea
successor, preserving the remote lineage instead of creating a parallel bootstrap.
