Kapso's MCP gates expose optional knowledge, research, experiment-history, and
repository-memory tools to coding agents. Each gate declares its dependencies
in the central registry, so a missing API key or executable is handled before
Claude Code starts instead of surfacing as a failed tool call during an
experiment.

## Gate registry

| Gate | Required environment | Server |
|------|----------------------|--------|
| `kg` | `KG_INDEX_PATH` | Bundled |
| `idea` | `KG_INDEX_PATH` | Bundled |
| `code` | `KG_INDEX_PATH` | Bundled |
| `research` | — | Bundled |
| `experiment_history` | `EXPERIMENT_HISTORY_PATH` | Bundled |
| `repo_memory` | — | Bundled |
| `bank` | `KAPSO_BANKS`, `KAPSO_SERVING_PULL_LOG`, `KAPSO_TASK_HARNESS`, `KAPSO_PROBE_BUDGET` (injected by Kapso per session from the loaded experience) | Bundled |
| `leeroopedia` | `LEEROOPEDIA_API_KEY` | Hosted (`mcp.leeroopedia.com`, nothing to install) |
| `inbox` | `KAPSO_INBOX_PATH`, `KAPSO_SESSION_ID`, `KAPSO_NODE_ID` (injected by Kapso per session) | Bundled |

The `inbox` gate carries one tool, `request_from_user`, through which an
implementation session asks you for a credential, access or a file; Kapso
injects the gate's three variables for each session when `inbox.enabled`
is true, so the gate always resolves. See the [inbox](/docs/build/inbox).

`GateDefinition.required_env` checks for a non-empty value. That establishes
that a dependency is configured; it does not make a network request or prove
that a credential is valid.

## What a campaign records

Every session's MCP tool calls are tallied per gate into the node's phase
telemetry (`<gate>_calls` and `<gate>.<tool>` under `ideation` and
`implementation`), so the checkpoint keeps what each node consulted. The
tally appears on the node-completed line in the log and status file, on each
attempt in `kapso trace`, and as "Knowledge consulted" totals in the final
summary. Leeroopedia answers carry the account's remaining credits, so the trace
and the summary also show "leeroopedia 761 → 747 remaining": the balance after
the campaign's first answer to the balance after its last. A configured gate
that cannot resolve is named once in the launch banner with its fix, for
example a missing `LEEROOPEDIA_API_KEY`.

## What the agent is told

Each gate owns its own "when to call these tools" text, one prompt file per
phase under the strategy's `prompts/gates/` directory, and a session's prompt
carries the guidance of exactly the gates it mounted. A gate that did not
resolve — no key, a `skip` policy, a Codex ensemble member that runs without
MCP — is not described, so the prompt never names a tool the session does not
have. Leeroopedia's guidance places its tools at decision points (plan before
code, priors before fixing a value, diagnosis on the first failed run) and
asks for `[PageID]` citations where an answer shaped the work.

## Failure policies

`resolve_gates` accepts three policies:

| Policy | Unavailable gate behavior | Diagnostic |
|--------|---------------------------|------------|
| `skip` | Omit the gate | Returned in `GateResolution` |
| `warn` | Omit the gate | Returned and logged as a warning |
| `error` | Stop configuration | Aggregate `GateCapabilityError` |

Unknown gate names and unknown policy names are always configuration errors;
they are never skipped.

```python
from kapso.gated_mcp import resolve_gates

resolution = resolve_gates(
    ["research", "repo_memory", "leeroopedia"],
    policy="warn",
)

print(resolution.enabled_gates)
for diagnostic in resolution.diagnostics:
    print(diagnostic.gate_name, diagnostic.enabled, diagnostic.reason)
```

The request order is preserved and duplicate names are removed. Diagnostics
contain dependency names only—never credential values.

## Building agent configuration

`get_mcp_config` resolves capabilities first and returns servers and allowed
tools only for enabled gates:

```python
from kapso.gated_mcp import get_mcp_config

mcp_servers, allowed_tools = get_mcp_config(
    ["idea", "experiment_history", "repo_memory"],
    kg_index_path="~/.kapso/experience/indexes/org-x/index.json",
    experiment_history_path="./.kapso/experiment_history.json",
    repo_root=".",
    gate_failure_policy="error",
    include_base_tools=False,
)
```

Explicit path arguments satisfy the corresponding environment requirement and
are forwarded only to the bundled MCP subprocess. Kapso uses the running Python
interpreter for that subprocess, which avoids relying on a separate `python`
executable on `PATH`. If all internal gates are omitted, no empty bundled server
is created. A hosted gate is handed to the CLI as a streamable-HTTP server under
its own name and tool-name prefix; its address and per-call timeout live in the
packaged config's `gates:` block, and `{VAR}` placeholders in the address are
filled from the gate's required environment when the session launches, so the
key rides on the URL and is never written into code or config.

## Generic search

The generic strategy defaults to `warn`, because its knowledge integrations are
optional enrichment:

```yaml
search_strategy:
  type: generic
  params:
    gate_failure_policy: warn  # skip | warn | error
    ideation:
      gates: [research, experiment_history, repo_memory]
    implementation:
      gates: [research, repo_memory]
```

Use `error` for a reproducible campaign where every configured knowledge source
is mandatory. Use `skip` when optional capabilities are expected to vary across
machines and warnings would be noisy.

## Use the gates from your own coding agent

The same gates are available to the session you work in, through the `kapso-mcp` console script that `pip install leeroo-kapso` puts beside `kapso`. It is a stdio MCP server; add it to your host once:

```bash
claude mcp add kapso -- kapso-mcp        # Claude Code
codex mcp add kapso -- kapso-mcp         # Codex CLI
```

A campaign session has its gate configuration built per session, with the campaign's paths and the interpreter Kapso runs in. A host's MCP file is static, so `kapso-mcp` derives the same configuration from where the session runs and from the config when it starts:

| Gate | Served when | Derived from |
|------|-------------|--------------|
| `research` | The `codex` CLI is on PATH | — |
| `repo_memory` | The repository holds `.kapso/repo_memory.json`, which a campaign builds | The git top level of the working directory |
| `experiment_history` | The working directory is inside a campaign directory | The nearest ancestor with `.kapso/experiment_history.json`; `models.embedding` from the config adds semantic search |
| `campaign` | Always | The campaign verbs as tools: `kapso_build_start` (a detached launch, its receipt returned), `kapso_status` (`kapso watch --json`), `kapso_stop`; `kapso_build_start` refused without `kapso` on PATH, all three refused inside a campaign directory; never served to a campaign's own sessions |
| `bank` | `--experience`, or the config's `experience.session_sources` when the flag is absent, loads a bank (`mine`, `mine:all`, a bank path or git reference) | One pinned clone per loaded bank, the serving record, the pull log and the intro staged under `learning.serving.session_root`, one directory per server process, removed when the server exits; the coordinate is the harness `--harness` names, `none` without one; the intro is the server's instructions, so the session names its sources on connect |
| `idea`, `code` | `--experience`, or the config's list, loads an index by name | The index's record |

Every gate left out is named on stderr and in the server's instructions with its reason, so `claude mcp list`, the host's log or the session itself says what it can and cannot reach; the server connects whatever is off. A listed source that does not exist leaves its gate off with the line that makes it. The `kg` gate (which carries the write tools) and the `inbox` gate (a session asking a person) are never served to a host. Leeroopedia is a hosted server, not a bundled gate: add it to the host as an HTTP MCP server at the address in the config's `gates:` block, with your key on the URL.

```bash
kapso-mcp --help
kapso-mcp --harness ./harness --experience mine,org-x --config kapso-config.yaml
```

`--root` names the session's directory when it is not the current one, `--experience` the sources to serve, comma-separated, in the forms `kapso experience list` shows, and `--harness` the harness the session works under (a name, a path or a git reference): its name is the coordinate `mine` serves cards by, as a build's is. Leeroopedia is a hosted server, not a bundled gate: loading it here only prints a reminder to add it to the host as an HTTP MCP server.

## Adding a gate

Dependencies belong beside the tool definition, not in a search strategy:

```python
GATES["example"] = GateDefinition(
    tools=["example_search"],
    server_name="example",       # hosted server; omit for bundled gates
    url=_HOSTED_GATES["example"]["url"],  # from config.yaml `gates:`
    tool_timeout_seconds=_HOSTED_GATES["example"]["tool_timeout_seconds"],
    required_env=["EXAMPLE_API_KEY"],
    guidance=_guidance("example", "ideation", "implementation"),  # prompts/gates/example.<phase>.md
)
```

For a bundled gate, also register its `ToolGate` class in `GATE_CLASSES`. For a
hosted gate, set both `url` and `server_name` and put the address in the
`gates:` block of `config.yaml`. Add hermetic resolution tests for missing and
available dependencies; live credential tests should remain opt-in.
